# ADR-017: INT8/SIMD最適化の実行計画を実測に基づき確定する

版: v2.0 追補 / 状態: 採用 / 前版から: 新規（ADR-010を実測で具体化。ADR-010自体は維持）

## ADR-010との関係

ADR-010が既に「F32でcorrectnessを確立し、prefix/scratch再利用後、hot linearへINT8/SIMDを適用する」と
決定している。**本ADRはその方針を変更しない。** ADR-010の時点で未確定だった次の3点を、実測により確定させる。

1. SIMDがICPのwasmで実際に使えるか（使える前提で計画してよいか）
2. どの演算が律速か（hot linearが本当に支配的なのか）
3. 目標に対する残差はいくらか（INT8で足りるのか、蒸留が要るのか）

## 背景

v2.0は受入目標を「1質問20B instructions以下、warm heap 2.5GiB以下、cold peak 3.0GiB以下」とし、
最適化の順序を「F32で参照実装との一致確認 → 固定prefix・buffer再利用 → 実測で重い演算をINT8/SIMD化 → まだ重ければ蒸留」と定めた。

その後、local replica上で `measured_instructions` を実測した結果（[PERFORMANCE_MEASUREMENTS.md](../../PERFORMANCE_MEASUREMENTS.md)）:

- 合成pack（hidden 512・4層・13M params）で **4.73B〜5.43B instructions/質問**
- 実checkpoint（28層・hidden 1024・128 tokens）への外挿で **494B〜567B instructions/質問**
- これは設計目標20Bの**25〜28倍**、ICPのupdate上限40Bの**12〜14倍**

つまりF32のままでは実checkpointを載せられないことが、最適化順序の第1段で確定した。

同時に、wasm-feature probe canisterをlocal replicaへinstall・実行して次を確認した:

| 命令 | 結果 |
|---|---|
| `i32x4.mul` | 実行成功 |
| `i32x4.dot_i16x8` | 実行成功 |
| `i16x8.extend_low/high_i8x16` | 実行成功 |
| `i16x8_dot_i8x16_i7x16_s`（直接のi8ドット） | **Rustでは未公開**（コンパイルエラー） |

**ICPのwasmはSIMDを実行できる。** v2.0は「SIMD専用kernel」を将来の最適化として挙げていたが、
その前提（使えるかどうか）が未確認だった。今回それが肯定された。

フェーズ別の内訳も実測した（`measure_phases`）。encoderが83%、decisionが16%で、
**softmax・norm・活性化・gather・decodeは合計1%未満**である。ADR-010の「hot linearへ適用」は
この内訳で裏付けられた。

ただし効率はすでに高く、これが本ADRの最も重要な発見である:

| フェーズ | 理論MAC | 実測 | instructions/MAC |
|---|---|---|---|
| encoder | 2,751,463,424 | 3,942,825,715 | **1.43** |
| decision | 805,306,368 | 742,253,057 | **0.92** |

> **この節の数値は誤りである。** 理論MACの分母が2つの理由で過大だった:
> `128` token固定の長さを27〜38-tokenの実測に当てていたこと、`wo` に `wi` と同じ幅を
> 課して分母を過大に数えていたこと（measure-mの条件で1.242倍）。正しい値は下の
> 「律速の特定」にある。
> 「下限から1.4倍以内」「INT8の伸びは最大3〜4倍」という結論もこの数値に依存しており、
> そのままでは成立しない。

## 決定

1. **INT8/SIMDは実施するが、それだけでは本番基準に届かない。** ×4（理論上限近く）を当てても
   421Mモデルは127Bで、40B上限の**3.2倍超過**である。したがって**INT8は単独の解ではない。**
2. **蒸留を必須の手段として採用する。** 規模を落とすことが支配的なレバーである:

   | 構成 | 投影 | 40B比 |
   |---|---|---|
   | 28層 h1024 現状 | 493B | 12.3倍 |
   | 28層 h1024 + INT8×4 | 127B | 3.2倍 |
   | 8層 h768 + INT8×3 | 約28B | 0.7倍 |
   | 6層 h640 + INT8×3 | 約15B | 0.4倍 |

   **正しい順序は「蒸留で規模を落とし、その上でINT8/SIMD」**である。INT8だけを先に完成させても
   本番基準には届かないため、順序を逆にしてはならない。
3. **INT8化と蒸留はいずれもbundleとcalibrationを変更する。** 設計の
   「カーネル/数値modeの変更はbundleとcalibrationを変更する」に従う。
4. **受入は1質問40B instructions以内**（ICPのupdate上限）。20Bは設計目標として維持するが、
   40Bを超えるものは本番採用しない。

## 律速の特定（追記・訂正済み）

サブフェーズまで測った結果、128-token profile の `measure-6l768` で **MLPが51%**、
attentionが31%、decision headが16%、その他が約2%である。したがってMLPが第一の対象。

**効率については当初の記載が誤っていた。** 測定ツールが理論MACを128 tokens固定で計算する一方、
実際の入力は27〜38 tokensだったため、instructions/MAC を約4倍過小評価していた。
さらに `wo`（`[hidden, intermediate]`）に `wi` と同じ `2*inter*h` を課しており、分母が過大だった
（measure-mの条件で1.242倍。MLP項だけの誤りなので4/3ではなく、その分だけ希釈される）。
両方を訂正した値:

| tier | instr/MAC（全体÷encoder MAC） | encoder単独 |
|---|---|---|
| measure-m | 4.94 | 4.11 |
| measure-6l768 | 4.88 | 4.10 |

**f32x4の下限は0.5 instructions/MAC**である（wasm SIMDにFMAが無いため `f32x4.mul` +
`f32x4.add` の2命令で4 MAC。「0.25」はFMA前提の誤り）。したがって現状は下限の**約10倍**。

gemm単体のA/B（measure-mの `wi` と同じ形状 `m=128, n=4096, k=512`、独立bench canister、
canister再installでカーネル固定を回避）:

| gemmのカーネル | instructions/MAC |
|---|---|
| wasm32 simd128 | **2.50** |
| scalar | 10.85 |

IC-Layaは既にSIMDカーネル側にあり、scalar比で**4.35倍**の短縮を得ている。残る余地は
「SIMD 2.50」から「下限 0.5」までの約5倍で、ここがINT8カーネルの担当領域である。
`-C target-feature=+simd128` はこれとは別問題で、有効化するとcandle-core 0.11.0が
E0433（`CurrentCpuF16`）でビルドできなくなる。詳細は
[PERFORMANCE_MEASUREMENTS.md](../../PERFORMANCE_MEASUREMENTS.md)。

「すでに最適に近いので実装を作り直しても速くならない」という当初の結論は**誤り**で、
正しくは**カーネル改善の余地が大きい**。

壁時計は公式の2B instructions/秒から決まる:

| 応答時間 | 必要なinstructions |
|---|---|
| 1秒以内 | 2B以下 |
| 3秒以内 | 6B以下 |
| 10秒以内 | 20B以下 |
| 30秒以内 | 60B以下 |

6層h768は128-token profileで**79.8B（約40秒）**であり、単独では上限40Bも超える。
カーネル改善（×5程度）とINT8（×3程度）を併用して初めて数秒台に入る。

## トレードオフと不採用案## トレードオフと不採用案

- **FP8 / FP4**: 不採用。両者はハードウェアのtensor core（Hopper/Blackwell、Apple M系列）を前提とした形式である。
  ICP canisterにGPUは無く、wasm32が持つ数値型はi32/i64/f32/f64のみ。FP8/FP4をwasmで扱うには
  ソフトウェアエミュレーションが必要で、**ネイティブf32より遅くなる**のが通常である。
  メモリ削減（F32 1.57GiB → FP8 約393MB → FP4 約200MB）は得られるが、律速は演算量なので効果がない。
  INT8だけは性質が異なり、整数演算がwasm命令に直接対応するため削減がそのまま効く。
- **蒸留を後段に回す案**: 不採用。実測により、INT8/SIMDの伸びでは40Bに届かないことが確定したため、
  蒸留は「後段の保険」ではなく**必須の手段**である。品質評価の負担は受け入れる。
- **INT4**: 不採用。wasmにはint4のドット積命令が無く、nibble展開のコストが利得を食う。
  f32x4が既に1.79 instr/MACなので、INT4の理論上限（レジスタあたり8 MAC）を当てても
  数倍が関の山で、精度劣化に見合わない。**レイヤー数を減らす方が効果が大きい。**
- **query callで推論する案**: 不採用。queryの上限は5Bでupdateの40Bより小さい。
  さらにqueryは状態を変更できずinter-canister callもできず、cacheもquotaも更新できない。
  加えて実行時間自体は変わらないため、速くもならない。
- **入力長・Score尺度・説明文の削減**: 不採用。意味を削る最適化は、性能を理由にしても認められない（v2.0の規定を維持）。
- **オフチェーン推論**: 本ADRの対象外。設計は「判断がオンチェーンで検証される」ことを主張しており、
  オフチェーン化はその主張を破棄する別の設計判断である。

## 検証条件

1. フェーズ別命令数の実測が出ていること（`artifacts/phase_measurements.json`）。**完了。**
2. INT8化の前後でlogitsを比較し、`from_logits` の分布が尺度上で意味を保つこと。
3. 再測定で **1質問40B instructions以内**。
4. 既存の回帰（`cargo test --workspace`、local replica統合試験）が維持されること。
   **fixtureの期待logitsを書き換えて通すことは認めない**（回帰検知が死ぬため）。
