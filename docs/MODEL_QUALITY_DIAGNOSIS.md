# 151Mモデルの性能切り分け

2026-09-23。今回のゲーム向け低成績を説明するような重みの取り違え、読み込み破損、
推論式の大きな誤り、量子化による大幅な精度低下は見つからなかった。
量子化前でもほぼ同じ誤答をするため、用途に対する元モデルの能力不足が主因と考えられる。
これは全用途・全プロンプトでの能力の上限を証明するものではない。

## 何を動かしているか

現在のpackは `heman10x/rlcd-modernbert-151m`、revision
`70fa19828074e1199e4a793c4af4dba3bfd1d222`。TypeSafeのJevそのものではない。
[公開元のREADME](https://github.com/Heman10x-NGU/openJev-verdict-2.0#two-models-in-this-project)
には、この151Mモデルと別アーキテクチャのVerdict 2.0が併記されている。
2.0の成績や `awesome-jev` 掲載作品の成績を、今のpackの実績とは扱わない。
読み込み先は設定どおりであり、別モデルへの差し替えは行っていない。

## 重み・tokenizer・読み込み

[固定revisionの公開ファイル情報](https://huggingface.co/api/models/heman10x/rlcd-modernbert-151m/tree/70fa19828074e1199e4a793c4af4dba3bfd1d222)
とローカルをハッシュ照合し、`model.safetensors`・`tokenizer.json`・`config.json` が一致した。
重みファイルはSHA-256、通常GitファイルはGit blob SHA-1で比較した。

packの142テンソルすべてについて、保存データのチェックサム、元テンソル名・形状を確認。
F32保存部分は元の値と完全一致、93個のINT8行単位量子化テンソルは各行の半ステップ相当の
誤差範囲内だった。元の143テンソルとの差は `model.logit_scale` のみで、
`normalize_features=false` のこの設定ではforwardで使わない。
今回調べたゲーム用packは行単位INT8であり、別の実験記録にあるblock-32 packと混同しない。

ラベル先頭の `<<LABEL>>`、本文との `<<SEP>>`、先頭 `[CLS]`・末尾 `[SEP]` の配置を確認。
本文をtokenizeする際には特殊トークンの自動追加を無効化し、両端を手動追加しており、
二重追加はない。先頭CLSのpooling、ラベル位置の取り出し、GELU、RoPE設定も照合した。

## 量子化前の独立参照

既存の `tools/diagnose_verdict.py` のNumPy参照を利用し、元checkpointのF32重みで計算した。
まず、作者の銀行分類データを固定順の先頭100件で再計算して参照自体を確認した。

| 指標 | 結果 |
| --- | ---: |
| F32参照と作者記録の選択一致 | 100/100 |
| 校正後top確率の最大差 | 0.0000020815 |
| F32参照の正解率 | 94/100 |
| `verdict-infer` INT8の作者記録との一致 | 99/100 |
| 同INT8の正解率 | 95/100 |

作者との一致率と正解率は別物。今回はINT8で1件選択が変わり、その1件は正解になった。
量子化の影響が常に無害という意味ではない。
温度は実ファイルの `1.4265148639678955` を使った。モデルカードにある別の値ではない。
正の温度で確率を調整してもargmaxは変わらず、温度調整だけではゲームの誤答は直せない。
また、銀行分類での確率校正がゲームの候補にも有効とは確認していない。

## ゲームの誤答は量子化のせいか

前回の説明付き候補の288回答を、**同じトークン列**で再計算した。

| 対象 | 元F32重みの正解 | INT8重みをF32演算した正解 | 前回のnative INT8正解 |
| --- | ---: | ---: | ---: |
| Terrarium | 72/96 | 72/96 | 72/96 |
| Last Exit | 47/96 | 46/96 | 46/96 |
| Hundred | 76/96 | 76/96 | 76/96 |

元F32と前回nativeの選択一致は287/288。INT8重みをF32演算した参照と前回nativeは288/288一致。
プラスチックの人参を食べる等の誤答は元のF32にも残る。
この試験では、演算カーネルや活性値の量子化よりも前の段階で同じ判断をしている。

銀行比較用の既存 `verdict-infer` とゲーム用 `tetris_probe` は別ビルド。
同じ6入力で選択は6/6一致したが、確率は完全一致ではなく最大約0.001624の差があった。
ゲームの主比較は、実際に前回使ったprobeの記録を対象としており、別ビルドの確率で置き換えていない。

中断からの再開時、両nativeツールが更新されていたため、最初の実験と再開後のビルドは
ハッシュで区別した。モデル・tokenizerは変更されていない。
更新後のprobeでも、固定した18入力の選択は前回の記録と18/18一致した。
1,000件の銀行分類照合は中断分を合算せず、更新後の実行ファイルをコピーで固定して
最初から別実験として実施した（`bank-full/`）。

更新後のINT8ツールでの1,000件照合は、作者の選択と **996/1000一致（99.6%）**、
欠落0件。4件の相違のうち1件は、作者の棄権から具体的な回答への変化だった。
top確率の最大差は0.060470。この残存差を無害・完全一致とは扱わない。
4分割は同一の固定実行ファイルと入力を使用し、各250件のログ・入力ハッシュを保存した。
各分割の終了コードは処理完了の確認用であり、`min_argmax_ratio=0` で実行している。
品質判断は合算した実測値によるもので、終了コードを品質合格の証拠とはしない。

## 入力形式の差か

各ゲーム24局面（前回の原文・通常候補順）について、F32参照で次を比較した。
追加実験では52トークンを超えても切り詰めず、最大62トークンをそのまま使用した。

| 形式 | Terrarium | Last Exit | Hundred |
| --- | ---: | ---: | ---: |
| `Question: ... / Context: ...` に分離 | 18/24 | 12/24 | 18/24 |
| 上記＋各候補に `It is` | 17/24 | 9/24 | 18/24 |
| 上記＋SDKのChoice同様に棄権候補を追加 | 13/24 | 2/24 | 18/24 |

[公開SDKのformatting](https://github.com/Heman10x-NGU/openJev-verdict-2.0/blob/main/core/formatting.py)
にある形式を試したが、この入力群では改善しなかった。
SDK形式のLast Exitは20/24で追加した棄権候補を選択した。
表はゲーム内の正解ラベルとの厳密一致であり、棄権とゲーム内の「情報不足」は別集計。
棄権が多いことだけから矛盾判断が改善したとは言えない。
説明文の書き換えを網羅した実験ではなく、今後のプロンプト改善の可能性は残る。

## 次の判断

今回の失敗を受けて、読み込みや量子化を大きく作り直す根拠はない。
このモデルをゲームに使うための追加UI実装も勧めない。
別のモデルを評価するなら、既存のゲーム局面をそのまま比較セットとして使い、
同じ基準を満たすことを確認してからデモを作る。今回、モデル変更・Canister更新は行っていない。

## 再実行と限界

```sh
python3 tools/verdict_quality_diagnosis.py
python3 tools/verdict_bank_check.py
```

NumPy、既存のmodel files・native tools・前回のsemantic-game-study記録が必要。
`artifacts/model-quality-diagnosis/` に入力の識別情報、F32/INT8のlogits、集計、
公開ファイル照合・重み検証を記録した。
NumPy参照を作者の記録で確認したが、PyTorch/ONNXの公式ランタイム自体は今回実行していない。
実Canister、全入力長、全分類数、日本語、全用途を検証したものではない。
